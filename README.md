# HeatShift AI

HeatShift is a heat-aware operational planning system for large outdoor sites. It combines one day of location-specific environmental conditions with fictional crews, jobs and constraints, then builds a validated lower-exposure schedule while preserving the operation.

- Product: <https://heatshift-ai-zeta.vercel.app>
- API: <https://heatshift-ai-api.vercel.app>
- Independent evaluator handbook: [docs/third-party-evaluator-guide.md](docs/third-party-evaluator-guide.md)

## Product loop

```text
choose a site → generate the operation → analyze weather + work → compare schedules → manager decision
```

The console is organized around one interactive state map. The three built-in sites—Phoenix, Houston and Miami—already contain a completed daily analysis using cached FortyGuard evidence. A user can also choose any supported US state or Washington, DC, place a site, select a historical date, generate a large fictional operation and run the same deterministic analysis.

The map exposes hourly conditions, exact cell temperatures, active work, the original schedule, the HeatShift proposal and every calculated metric. The Operation & method view explains the generated crews and jobs, weather evidence, score construction, optimizer and before/after result.

## Data disclosure

HeatShift keeps three layers distinct:

- **Provider evidence:** cached FortyGuard heat cells and hourly environmental conditions for the three built-in demonstrations.
- **Fictional operations:** crews, worker counts, PPE, acclimatization, workloads, jobs, locations, mobility and scheduling windows.
- **HeatShift-derived results:** task-hour screening scores, Site Thermal Burden, Crew Exposure Load, disruption components and the proposed schedule.

New-site conditions are currently generated by a transparent location/date-aware simulation. They are never labelled as FortyGuard evidence. The console header reports **Simulated run** when FortyGuard is unavailable, unconfigured or out of credits and explains the reason. **Retry** performs a fresh read-only provider check; only a successful response changes the header to **FortyGuard live**.

No provider job is submitted by this availability check, and TLS verification is never bypassed.

## Decision metrics

- **Task-hour screening score:** a versioned 0–100 policy using apparent temperature, spatial cell offset, workload, PPE, acclimatization and sun/shade.
- **Site Thermal Burden:** `Σ max(0, hourly apparent temperature − 35°C) × 1 hour`.
- **Crew Exposure Load:** `Σ (task score ÷ 100) × duration hours × crew size`.
- **Operational Disruption:** shifted minutes and crew reassignments, reported separately.
- **Outcomes:** original/proposed high-risk worker-minutes, high-risk worker-hours avoided, percentage reduction at score 50, jobs moved, fixed jobs preserved, residual alerts, work retained and hard-constraint validity.

The 35°C burden baseline and score-50 threshold are disclosed product settings, not medical or regulatory limits.

## Optimizer

The deterministic single-day optimizer considers 30-minute candidate starts and eligible crews. Its lexicographic objective is:

1. preserve all encoded hard constraints;
2. minimize worker-minutes at score 50 or higher;
3. minimize total Crew Exposure Load;
4. minimize the highest individual crew load;
5. minimize shifted minutes and crew changes.

Fixed jobs stay fixed, durations do not change, crews cannot overlap, jobs remain inside their allowed window and only eligible crews may be assigned. The result is the best validated feasible plan found by bounded search, not a claim of global mathematical optimality.

## Empirical validation

The homepage reports a separate benchmark using 566 controlled human-exposure sessions from the public HEAT-SHIELD dataset. Without fitting the HeatShift policy on those records, the score had a 0.7718 Spearman rank correlation with measured one-hour physical-work-capacity loss; sessions at or above score 50 averaged 36.45 percentage points more measured loss than sessions below it.

This is descriptive association. It does not establish causality, medical accuracy, injury prevention or universal safety effectiveness. See [docs/real-data-validation.md](docs/real-data-validation.md).

## One-command local setup

Prerequisites: Python 3.13 and Node.js 20.9 or newer.

Linux or macOS:

```bash
./scripts/start-local.sh
```

Windows PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start-local.ps1
```

Each launcher creates `.env` when necessary, creates the repository-local `.venv`, installs dependencies, loads one environment for both services, starts FastAPI on port 8000 and Next.js on port 3000, and stops both together with Ctrl+C.

Provider and LLM keys are optional for local evaluation. With no FortyGuard key, the product starts in clearly labelled simulated fallback mode. Add secrets only to the ignored `.env` file; never commit them.

## Architecture

- Next.js 16 and React 19 frontend.
- Leaflet/OpenStreetMap interactive map with GeoJSON heat cells; no WebGL dependency.
- FastAPI API and deterministic daily simulation/optimization engine.
- Supabase anonymous identity, RLS isolation and durable custom-workspace snapshots.
- Groq-compatible optional activity naming; deterministic names and briefings remain available without an LLM.
- Vercel Hobby frontend and backend deployments.

Hosted custom daily workspaces are stored as RLS-scoped Supabase snapshots, so site creation, generated operations and completed analyses survive Vercel instance changes and cold starts. Local development without Supabase remains process-local. The three curated examples are reconstructed from checked-in evidence on every start.

## Safety boundary

HeatShift provides screening-level planning support. It is not a live sensor, forecast, building measurement, medical system, injury predictor, regulatory exposure limit, or substitute for on-site WBGT measurement, emergency procedures and qualified safety judgment.
